This document maps every Stitch-exported screen to its implementation, records every deliberate deviation/judgment call, and lists the utility pages that exist outside the Stitch export. It is the canonical fidelity record for this repo — read it before assuming a discrepancy between the app and `screen.png`/`code.html` is a bug rather than a documented, deliberate call.

## Design tokens

All colors, type scale, spacing, radii, and shadow tokens in `tailwind.config.ts` are copied verbatim from the `tailwind.config` block embedded identically in every screen's `code.html` (cross-checked, they matched exactly across all 7 screens). Nothing was renamed, rounded, or "cleaned up" — the file header comment says so explicitly to deter future edits.

## Component architecture

Per the brief's core constraint, components are only shared across screens where the Stitch source genuinely repeats the same visual (e.g. `Icon`, `SearchResultCard`'s underlying patterns, `NeighborhoodCard`, `RecentListingRow`). Each screen's bespoke property/listing card is its own page-scoped component rather than a forced shared abstraction:

- `components/property/property-card.tsx` — accueil-style card
- `components/property/rent-listing-card.tsx` — louer-style card
- `components/search/search-result-card.tsx` — recherche-style card (also reused by `/favoris`, since it already handles the favorite-toggle affordance)
- `components/property/contact-agency-panel.tsx`, `components/property/ai-question-form.tsx` — villa-detail sidebar/AI-box interactivity
- `components/passport/trust-score-gauge.tsx`, `components/passport/verification-timeline-step.tsx` — passeport screen
- `components/louer/ai-alert-form.tsx` — louer's Ogooué AI alert box

## Data model

Centralized under `data/`: `properties.ts`, `land.ts`, `neighborhoods.ts` (implied), `provinces.ts` (implied), `agencies.ts`, `passport-timeline.ts`, `image-manifest.ts`. All page components read from these rather than hardcoding copy inline, so filters/sorts/search on `/recherche`, `/acheter`, `/louer`, `/terrains` operate on real (if mock) data rather than static markup.

### Gabon administrative geography (real, sourced data)

`data/gabon_provinces_villes_quartiers.source.json` is a real, sourced reference dataset (9 provinces → 52 villes/communes → 821 quartier entries), compiled 2026-09-24 primarily from the Journal Officiel (loi n°020/2025) plus municipal and public/press sources for complementary entries — **not mock data**, and never edited by hand (kept as a verbatim JSON import so the 821 quartier strings can't drift from the sourced original). Per its own methodology, no quartier is ever invented: an empty `quartiers` array means "no verifiable source found," not "this ville has none." `data/gabon-geography.ts` wraps it with types and helpers (`GABON_GEOGRAPHY`, `GABON_PROVINCE_NAMES`, `GABON_VILLES`, `getVillesByProvince`, `getQuartiersForVille`, `formatVilleLabel`).

This replaced several small, partial hardcoded location lists:

- `components/home/hero-search.tsx` — "Localisation ou Province" now lists all 9 real provinces (was 4), each as a real `{value, label}` pair (`value` = the exact province name every destination page's `province` filter expects, `label` = the Stitch-style "Province (villes...)" descriptive text).
- `app/acheter/page.tsx` — "Localisation" now lists all 52 real villes grouped by province via `<optgroup>` (was 4 villes); the "Explorer les 9 provinces" quick-nav links were also fixed to pass the real province name instead of a slug (see Deviations #11).
- `app/terrains/page.tsx` / `components/terrains/search-form.tsx` — "Province" + "Ville / Zone" are now a real client-side cascading pair (`GABON_GEOGRAPHY` → `getVillesByProvince`) instead of two disconnected fields (Province listed all 9 provinces but "Ville / Zone" was a static, unrelated 4-item mock `ZONES` array that never changed when Province changed). See Deviations #12.
- `components/publier/publish-form.tsx` — "Localisation" was a single free-text input; it is now a real Province → Ville cascading select, followed by a real Quartier select (populated from the sourced list) with an "Autre (préciser)" escape hatch, or — when a ville has no verified quartier list — a free-text field paired with an honest note explaining the data gap rather than silently offering nothing or fabricating options.
- `app/louer/page.tsx` — "Localisation ou Quartier" wiring was first fixed (the `<select>` used `name="localisation"`, which the page never read; see Deviations #11), then its options were expanded from Libreville-plus-2-hardcoded-cities to all 9 provinces (grouped by `<optgroup>`, same pattern as `/acheter`) — Libreville keeps its own curated quartier list from `data/neighborhoods.ts`, every other real ville is now reachable. See Deviations #12.

The Stitch source's footer (`components/layout/footer.tsx`) deliberately still lists only its literal 4 provinces (Estuaire, Haut-Ogooué, Ogooué-Maritime, Woleu-Ntem) — that list is real, visible, pixel-placed copy straight from `code.html`, not a closed dropdown, so expanding it to all 9 would be a fidelity deviation rather than an improvement.

## Deviations & judgment calls (flagged deliberately, not oversights)

1. **`/terrains/[slug]` is a new route** — the Stitch export only shows a terrains *listing* screen, no land-detail screen. A detail page was built following the same visual language as the listing cards, since linking a land card to a dead end would violate the "no dead links" constraint.
2. **`/bien/[slug]` was generalized from one villa to all properties** — the Stitch source shows one specific villa's detail page. `generateStaticParams()` covers every property in `data/properties.ts`, with every optional section (`description`, `features`, `amenities`, `passportChecklist`, `gallery`, `neighborhoodBlurb`) rendered conditionally so properties with thinner data degrade gracefully instead of showing blank sections.
3. **Passeport eligibility gating** — `/bien/[slug]/passeport` only exists for properties where both `passportScore` and `reference` are defined (`passportEligible()` in both `app/bien/[slug]/page.tsx` and the passeport page itself). This naturally yields exactly the two properties that have full passport data, rather than fabricating a reference number for every property or hardcoding a single slug.
4. **Villa-detail's "Contacter le conseiller dédié" / passeport CTA** — the Stitch source has this as a dead `href="#"`. Changed to a real `<Link>` to `/bien/[slug]`.
5. **The 4 static sidebar CTA buttons** (Réserver une visite / WhatsApp / Appeler / Message) on the villa-detail screen have no backing phone/email data in the Stitch source. Rather than fabricate contact details or leave them inert, `ContactAgencyPanel` wires all 4 to one `useState` flag that swaps the button block for an honest inline confirmation ("Votre demande a été transmise à {agence}. Un conseiller vous recontactera sous 24h."). The same "genuine state change, no fabricated backend" pattern is reused in `AiQuestionForm`. The lead-capture forms on the utility pages (see below) go one step further and actually persist the submission on-device — see judgment call #13.
6. **Villa-detail's "Localisation & Quartier" map** — the source's own map placeholder div is blank/empty (no real image reference). Reused the already-canonical `misc_carte_illustrative_libreville` illustrative-map asset (also used on `/terrains` and `/recherche`) for visual consistency rather than shipping an empty box or introducing a new, unrelated image.
7. **`/recherche`'s 4th map pin** ("120M FCFA", illustrative-only in the source) has no backing property in `data/properties.ts`. The 3 pins that do map to real properties are genuine `<Link>`s to `/bien/[slug]`; the 4th was dropped rather than inventing a listing or shipping a dead pin.
8. **Loan/budget simulator on `/acheter`** — the Stitch source shows a simulator UI without a specified formula. A real, simple amortization-style calculation was implemented (not left as a static mockup) so the "simulate" affordance is genuinely functional.
9. **9-province tile split on the home/search province sections** — the source mixes icon-only and photo tiles inconsistently across provinces; implementation splits provinces into an icon-tile set and a photo-tile set based on which already have a real image asset in `data/image-manifest.ts`, rather than forcing a mismatched image onto every tile.
10. **"Voir tout le catalogue" → `/recherche`** — a few catalogue-wide CTAs across screens point at `/recherche` (the most complete filterable listing view) rather than a screen-specific listing route, where the source's intent was clearly "see everything," not a specific new screen.
11. **Two pre-existing dead/no-op location filters, found and fixed while integrating the real Gabon geography data**: `/acheter`'s province quick-nav grid linked to `/recherche?province=<slug>` (e.g. `estuaire`) while `/recherche` and every property's `province` field use the full display name (e.g. `Estuaire`), so the filter silently never matched; and `/louer`'s location `<select>` submitted `name="localisation"`, a param the page never read (it reads `quartier`), so the field did nothing. `/recherche` itself was also not reading its own `province` query param at all — added that filter. All three now function for real, consistent with the "no dead interactive element" constraint.
12. **Cross-page location/type/budget synchronization** — auditing every location and type selector across the app surfaced that (a) `/terrains`'s "Province" and "Ville / Zone" fields were visually paired but logically disconnected: Province was already wired to the real `GABON_GEOGRAPHY` dataset, but "Ville / Zone" was a separate static 4-item `ZONES` mock array that never updated when Province changed, and never matched any real `Land.location` string; (b) `components/home/hero-search.tsx`'s "Localisation ou Province" value was pushed as a `location` query param that **no destination page ever read** — the field was fully decorative; (c) hero-search's single `PROPERTY_TYPES` list was pushed as `type` to whichever tab was active, but `/louer`'s type filter does an exact match against a different, shorter vocabulary (`Appartement`, `Maison`, `Studio`, `Villa`, `Meublé`), so searching from the Louer tab silently produced wrong/empty results; and (d) `/acheter`'s own hero form had "Type de bien" / "Budget max" / "Ogooué AI Query" fields that were rendered but never read by its filter logic at all, and didn't round-trip their submitted value back into the field. Fixed by: introducing `data/property-types.ts` as the single source of truth for each destination's real type vocabulary (`ACHETER_TYPE_OPTIONS`, `LOUER_TYPE_OPTIONS`), which hero-search now looks up per-tab (resetting `propertyType` on tab switch); replacing `/terrains`'s static `ZONES` array with a real `TerrainsSearchForm` client component cascading Province → Ville off `getVillesByProvince` (same pattern as `publish-form.tsx`); renaming hero-search's pushed param from `location` to `province` (a param `/acheter`, `/louer`, and `/terrains` all already read or were updated to read); and wiring `/acheter`'s type/budget/free-text-query filters for real, with `defaultValue`s that reflect the actually-applied filter after submission. A shared `parseBudgetLabel()` helper (`lib/format.ts`) normalizes budget values regardless of phrasing (`"150 000 000"`, `"Jusqu'à 300 000 FCFA / mois"`, `"Tous budgets"`) across all three pages. Confirmed via direct `code.html` inspection that no layout change was needed: `/acheter` and hero-search each have exactly one location field (province-level display is itself Stitch-faithful), `/louer` has exactly one location field, and `/terrains` genuinely has two — so real cascading was only introduced where the source itself shows two fields.

13. **Local relational data layer (`lib/local-store/`, `data/local/`)** — the initial build's confirmation-only forms (judgment call #5) have been replaced by a real, if local, persistence layer: every "submit" interaction (publishing a listing, the 4 lead forms, favoriting) now writes a genuine record to `localStorage`, keyed to an anonymous per-device `ownerId` (a lazily-created UUID, not a login — see `lib/local-store/session.ts`), instead of an ephemeral `useState` confirmation that forgets it happened. `createStorageChannel`/`createIdSetStore`/`createRecordStore` generalize the pattern already proven by the original favorites implementation; entity modules (`favorites-store.ts`, `published-listings-store.ts`, `leads-store.ts`) sit on top and are the only thing calling components ever import. This is deliberately shaped as a 1:1 stand-in for real database tables (`id`, `createdAt`, `ownerId` on every record; a single `leads` table with a `kind` enum and jsonb-shaped `payload` rather than four near-duplicate tables) so that connecting a real Supabase project later is a matter of swapping each store's internals for real queries — every call site (`usePublishedListings()`, `useLeads()`, `useFavorites()`) stays the same. Published listings are honestly marked `status: "en_attente_verification"` and merge into `/`, `/acheter`/`/louer` (by transaction type), `/recherche` and their own `/bien/[slug]` page (resolved client-side via `LocalPropertyDetailGate` for slugs outside the static `properties` array) without disturbing the curated Stitch-faithful pool on any of those pages. `/mes-annonces` and `/mes-demandes` (see Utility pages) exist so this data is actually visible somewhere instead of being a store nobody can see.
14. **`/recherche`'s satellite/cadastre map layers** — the Stitch source only shows one static map illustration, no alternate layers. Rather than fabricate satellite imagery or cadastral geodata that doesn't exist, "Satellite" and "Cadastre" apply a real CSS `filter` transformation (saturation/contrast/hue-rotate, and grayscale+contrast plus a drawn grid-line overlay, respectively) to the same one real `misc_carte_illustrative_libreville` asset used everywhere else — a genuine, visibly-different treatment of real data rather than invented imagery. The zoom controls (real CSS `scale`, clamped and disabled at real min/max) and "Me localiser" (real `navigator.geolocation.getCurrentPosition()`, showing the actual detected coordinates or an honest denied/unsupported message — never a fabricated pin, since the illustrative map image is not georeferenced) follow the same "real interactivity, no fabricated data" principle.
15. **Land domain enrichment (`/terrains/[slug]`)** — each `Land` now carries a `disputeRisk` (faible/modéré/élevé + a real-world explanation) and a `landChecklist` of concrete Gabonese land-tenure verification items (bornage contradictoire, quitus fiscal foncier, certificat de non-litige, mutation en titre foncier, etc.), rendered as two new sections on the (already-new, see #1) `/terrains/[slug]` page. A third seed entry, `parcelle-coutumiere-village-akok-oyem`, was added at trust level 1 ("Coutumier Brut") — until now every seeded land sat at level 4 or 5, so the 5-level trust ladder had no real low-trust example to actually show a visitor what a risky, unregistered customary-tenure listing looks like and how it's flagged. Reuses the already-canonical `misc_hero_foret_vers_terrain_defriche` asset (previously only a decorative hero background) rather than introducing a new image.

16. **Rental caution/deposit disclosure + real persistence for villa-detail contact actions** — each of the app's 6 rental (`transactionType: "location"`) properties now has a `cautionLabel` (a real Gabonese rental-market deposit convention: typically 1–3 months of rent plus one month paid in advance, varying with furnished/unfurnished status), surfaced in `ContactAgencyPanel` right under the price — genuinely useful information the panel didn't disclose before. Separately, `ContactAgencyPanel`'s "Réserver une visite" / "Message" / no-phone-fallback buttons were the one remaining interaction from judgment call #5 that still only flipped a `useState` and forgot it happened after Batch 5's real WhatsApp/tel links (judgment call #13) — they now also call `insertLead("contact-bien", ...)`, so every such request is a real persisted record, visible (with a link back to the property) in `/mes-demandes`'s new "Demandes sur des biens" section, consistent with how the other 4 lead forms already behave.

17. **Deployment/SEO metadata layer** — none of this has a Stitch equivalent (Stitch exports static screens, not a deployable site), so it's additive rather than a deviation from any visual source. Every route now has real per-page `<title>`/`<meta description>` via the App Router `Metadata` API: the root layout sets a `metadataBase` (derived from the actual linked Vercel project name in `.vercel/project.json`, flagged inline for correction if a custom domain is attached later) and a title template (`"%s | Ogooué Habitat"`); static server-component pages export `metadata` directly; the three client-component pages that can't (`/favoris`, `/mes-annonces`, `/mes-demandes`) get a sibling `layout.tsx` instead; the three dynamic routes (`/bien/[slug]`, `/bien/[slug]/passeport`, `/terrains/[slug]`) get `generateMetadata` built from the real property/land data, with an honest generic fallback (never a fabricated title) for locally-published slugs outside the static array. `app/sitemap.ts` enumerates every static route plus every real `properties`/`lands` slug (and passport-eligible slugs); `app/robots.ts` points at it and excludes the three per-device-only pages above, since their content is local to a visitor's browser and has nothing to index. `app/not-found.tsx`/`app/error.tsx` replace Next.js's default boilerplate with branded pages using the existing design tokens and `Icon` component.

18. **Header hover mega-menus (`data/nav-menu.ts`)** — the Stitch header nav is a flat link row with no dropdown behavior, so this is additive, not a redraw of any Stitch screen. Each of the 7 primary nav items now reveals a full-width hover panel (desktop only, `xl:` breakpoint, closes automatically once the pointer leaves the header) built from data that already exists and already does something real: `/acheter` and `/louer`'s columns link to `?type=`/`?province=` values consumed by `lib/property-filters.ts`'s existing `matchesAcheterFilters`/`matchesLouerFilters`; `/terrains`'s column names the real 5-level `TRUST_LEVELS` and both it and `/acheter`'s "Simuler mon prêt"/`/louer`'s "Créer une alerte" highlight card link to real in-page section ids (`#echelle-confiance`, `#simulateur-pret`, `#alerte-ai`, `#carte`, `#notifier`, `#a-venir`, `#pourquoi`, `#rejoindre`, `#demande`) added to the corresponding existing sections purely as scroll anchors — no new copy was invented; `/recherche`'s two columns reuse the exact same quick-filter chip labels/query-params (`?villa=1`, `?shield=1`, etc.) already on that page. `/neuf`, `/professionnels`, `/diaspora` (single-page, no filterable sub-content) get a shorter one-column menu naming their existing real feature bullets instead of a fabricated sub-navigation. Deliberately does **not** copy the reference site's pattern of listing services that don't exist here (no "estimation," "défiscalisation," "viager," etc.) — every link changes what the destination page actually shows.

19. **Property/land comparator (`/comparer`, `data/local/compare-store.ts`)** — audited against SeLoger-style portal capabilities (user request), this was a genuine gap: no comparison feature existed anywhere. Additive, not a redesign of any existing screen: a `CompareButton` (same visual language as the existing `FavoriteButton`) sits alongside the heart icon on all 5 card components (`property-card`, `buy-listing-card`, `rent-listing-card`, `land-card`, `search-result-card`), backed by a real localStorage-backed store (same `createStorageChannel` primitive as favorites/leads/published-listings) capped at 4 items. A floating `CompareTray` (mounted once in `SiteShell`, so it appears everywhere without touching any individual page) shows the live count and links to `/comparer`, which resolves the real selected properties (via the existing `useMergedProperties()`, so locally-published listings are comparable too) and lands (`data/land.ts`) into a side-by-side table — price, type/province, specs, and either Passeport Ogooué score or land trust level depending on kind. Reuses the existing `property:slug` / `land:slug` composite id scheme from `data/local/favorite-id.ts` rather than inventing a parallel one.

20. **Real saved-search alert payload (`/louer`'s Ogooué AI alert, `components/louer/ai-alert-form.tsx`)** — audited against major-portal capabilities, the existing alert form only captured an email address and threw away the criteria the visitor had actually just searched with (`insertLead("louer-alerte", email, {})`). Fixed additively, no visual redesign: `/louer/page.tsx` now passes the page's own already-computed real filter state (secteur/quartier, type de bien, budget) and the real current match count (`filtered.length`, from the existing `matchesLouerFilters`) down to the form, which persists all of it in the lead's `payload` via the existing `leads-store`. `/mes-demandes` (which already rendered arbitrary lead payloads generically) gained matching field labels and now doubles as a real "my saved searches" view, plus a delete button (new `removeLead()` on `leads-store`) so any lead, including alerts, can be removed. The static "Alerte Instantanée Active" illustrative card next to the form (fixed example values, e.g. "Batterie IV / Louis") is left untouched — it's a separate promotional mockup, not the record created by submitting the form, and isn't presented as this visitor's own data.

## Utility pages (no Stitch source — flagged explicitly)

The header/footer nav references several routes with **no corresponding Stitch screen at all** (confirmed: the export only contains the 7 screens listed above). These were built from scratch to avoid 404s from already-faithful pages' own navigation, following the same visual tokens and the same "honest confirmation, no fabricated backend" interactivity pattern established for the Stitch screens:

- `/favoris` — reads real favorited properties via `useFavorites()` (the same localStorage-backed hook wired into `SearchResultCard`'s heart button), with a genuine empty state.
- `/connexion`, `/inscription` — real forms with client-side state; submitting shows an honest "this is a demo environment" message rather than faking a session or account.
- `/diaspora` — full value-proposition page for the "Ogooué Diaspora" differentiator (named in the brief) plus a real lead-capture form.
- `/neuf` — framed as an active "waitlist / be notified first" feature (deliberately avoiding literal "Coming soon" text) rather than fabricating new-build listings that don't exist in the data.
- `/professionnels` — B2B value-prop page + a real "Devenir partenaire" lead form.
- `/publier` — full property-submission form; submitting now really persists the listing on-device (see judgment call #13) and the confirmation is framed around genuine Ogooué Shield verification (pending, ~48h average) rather than a false claim of instant publishing.
- `/mes-annonces` — a visitor's own locally-published listings (from `/publier`), linking to each `/bien/[slug]`, with an honest empty state and "conservé uniquement sur cet appareil" copy.
- `/mes-demandes` — a visitor's own submitted leads (Diaspora, Professionnels, Ogooué Neuf waitlist, Louer AI-alert), grouped by kind, same on-device-only honesty copy. The header's account icon routes here or to `/mes-annonces` (whichever has content) instead of always going to `/connexion`.
- `/legal/mentions-legales`, `/legal/confidentialite` — static, substantive (non-Lorem-ipsum) legal pages, the latter referencing Gabon's real data-protection law (Loi n°001/2011) and explicitly documenting the app's actual localStorage-based favorites mechanism.
- `/aide` — a help center inspired by the structure of established real-estate portals (search-driven hero, "professional" vs. "individual" entry points, categorized FAQ), but with every answer describing this app's actual, already-implemented behavior (Ogooué Shield gating, the land trust ladder, rental caution disclosure, on-device-only persistence, Passeport Ogooué eligibility) — no invented support channel or fabricated partner-logo strip like the reference had, since no such real partnerships exist here. Live client-side search (accent-insensitive) and an accordion FAQ list are real interactivity, not decorative. Linked from a new small "Aide & FAQ" pill in the header (desktop + mobile) and a 4th row in the footer's "Administratif & Légal" column, matching the existing 4-row rhythm of its sibling columns.

None of these introduce new color/typography tokens or new images beyond what's already in `data/image-manifest.ts`.

## Known limitations

- **`screen.png` thumbnails are not pixel-diff-able.** Each Stitch screen's `screen.png` is a non-uniformly scaled preview image (different sizes/aspect ratios per screen), not a literal 1440px capture. `tests/visual/screens.spec.ts` therefore checks structural fidelity (literal copy present, no console errors, no horizontal overflow) plus a self-referential screenshot baseline for future-regression detection — it does not, and cannot, diff against the Stitch thumbnails directly. Fidelity to `screen.png`/`code.html` was otherwise verified by direct reading of every screen's full `code.html` source during implementation.
- Mock data only — there is no real backend/database/auth. Submissions (published listings, the 4 lead forms, favorites) are genuinely persisted, but only on-device via `localStorage`, keyed to an anonymous per-device id rather than a real account (see judgment call #13); they are invisible to anyone else and disappear if the visitor clears their browser data.
